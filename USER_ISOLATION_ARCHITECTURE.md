# User Isolation & Application ID Architecture - Complete Documentation

## Overview

The system implements **multi-tenant isolation** with perfect user separation and application management. Each authenticated user gets their own user_id and application_id with zero possibility of conflicts or cross-user access.

---

## 1. User ID Generation & Management

### User ID Source: **Supabase Auth** ✅
- **Generated by:** Supabase Authentication service automatically
- **Format:** UUID v4 (e.g., `ae6f9802-4c14-437c-9480-ebae9fad131d`)
- **Uniqueness:** Guaranteed globally unique, cryptographically secure
- **Ownership:** Each user_id is tied to their email/auth credentials
- **NOT under our control** - Supabase manages this transparently

**Key Property:** 
```
- No two users can have the same user_id
- user_id is immutable and persistent across sessions
- Supabase ensures this automatically
```

---

## 2. Application ID Generation & Management

### Application ID Source: **Supabase Database** ✅
- **Generated by:** PostgreSQL `uuid_generate_v4()` (configured in Supabase)
- **Format:** UUID v4 (e.g., `aa852bf7-01f9-4f67-aa92-b059cfd7d324`)
- **Uniqueness:** Guaranteed globally unique
- **Ownership:** Each application_id is linked to a specific user_id via Foreign Key
- **Handled by Backend:** Our code creates applications, DB generates IDs

**Key Property:**
```
- No two applications can have the same application_id
- Each application_id must reference exactly one user_id
- Database constraints enforce this relationship
```

## 3. User Isolation Architecture

### Three-Layer Protection

#### Layer 1: **Database Schema (Strongest)**
```sql
-- Applications table has user_id as Foreign Key
CREATE TABLE applications (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    user_id UUID NOT NULL REFERENCES auth.users(id),
    status VARCHAR(50),
    created_at TIMESTAMP,
    submitted_at TIMESTAMP
);

-- Unique constraint: Each user has one active application
ALTER TABLE applications ADD UNIQUE (user_id, status);
```

#### Layer 2: **Row Level Security (RLS) Policies (Enforced)**
```sql
-- SELECT: Users can only see applications where auth.uid() matches user_id
CREATE POLICY "Users can view their own applications" ON applications
    FOR SELECT USING (auth.uid() = user_id);

-- INSERT: Users can only create applications with auth.uid() as user_id
CREATE POLICY "Users can insert their own applications" ON applications
    FOR INSERT WITH CHECK (auth.uid() = user_id);

-- UPDATE: Users can only modify their own applications
CREATE POLICY "Users can update their own applications" ON applications
    FOR UPDATE USING (auth.uid() = user_id);
```

**How RLS Works:**
- Automatically filters queries based on authenticated user
- Even if SQL injection occurs, RLS blocks unauthorized access
- No user can query/insert/update another user's data

#### Layer 3: **Backend Application Logic (Redundant Safety)**
```python
# Backend validates ownership before every operation

def get_user_application(user_id: str):
    """Gets the user's application based on their user_id"""
    result = supabase.table("applications")
        .select("*")
        .eq("user_id", user_id)  # Filter by user_id from JWT
        .execute()
    return result.data[0] if result.data else None

def get_application_by_id_and_user(application_id: str, user_id: str):
    """Verifies ownership before returning application"""
    result = supabase.table("applications")
        .select("*")
        .eq("id", application_id)
        .eq("user_id", user_id)  # Double-check ownership
        .execute()
    return result.data[0] if result.data else None
```

## 5. Conflict Prevention Mechanisms

### Scenario 1: Same User, Multiple Tabs/Devices

**Problem:** User has app open in Tab A and Tab B, submits in both

**Solution:**
```
Tab A submits → Backend processes → Database updates applications
                                     ↓
Tab B tries to submit → Backend processes → Database updates applications
                      (Both operations succeed, data in final state)

✓ NO CONFLICT - Each operation is idempotent
✓ User still has ONE application_id
✓ Latest data wins (deterministic)
```

**How it's handled:**
```python
# UPSERT operation - always safe
supabase.table("students").upsert(data).execute()
# If record exists, update it
# If record doesn't exist, insert it
# Result: Single source of truth maintained
```

## 7. RLS Policies in Action

### Example: Medical Data

```sql
-- Only accessible if you own the application
CREATE POLICY "Users can insert their own medical info" ON medical_info
    FOR INSERT WITH CHECK (
        EXISTS (
            SELECT 1 FROM applications
            WHERE applications.id = medical_info.application_id
            AND applications.user_id = auth.uid()
        )
    );
```

**What this means:**
```
User1 tries to insert medical data for User2's application:
  INSERT INTO medical_info (application_id, data)
  VALUES ('aa852bf7-user2-app', {...})
  
Database checks:
  - Does application 'aa852bf7' exist? YES
  - Does it belong to auth.uid() (User1)? NO
  - RLS blocks: INSERT FORBIDDEN ✓

Even if User1 knows User2's app_id, they cannot insert data into it
```
